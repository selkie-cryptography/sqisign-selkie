\section{Post-Baseline Performance and Constant-Time Work}
\label{sec:post-baseline}

With baseline interoperability achieved (\S\ref{sec:status}), the
implementation moves into a post-baseline phase: performance
optimization and constant-time hardening built on top of the
byte-equality foundation.  Each change is interop-safe (KAT bytes
preserved) unless explicitly noted under
\S\ref{sec:tried-rejected}.  The field-arithmetic and elliptic-curve
layers are already constant-time (the Montgomery ladder runs a fixed
bit count; \texttt{subtle::ConstantTimeEq} guards secret comparisons);
the quaternion-arithmetic layer is the primary remaining variable-time
surface, which the optimizations below progressively harden.

We first present the optimizations that improved performance or closed
a timing leak (\S\ref{sec:perf-ct}), then the alternatives we evaluated
and rejected (\S\ref{sec:tried-rejected}).  The negative results are
recorded because each documents a design decision and spares a reader
the same dead end.

\subsection{Performance and constant-time optimizations}
\label{sec:perf-ct}

Performance figures are either deterministic instruction counts --
Valgrind via \texttt{gungraun}, or hardware instructions-retired via
\texttt{/usr/bin/time -l} -- or wall-clock A/B medians; each result
states which. Wall-clock figures are flagged because they are sensitive
to runner conditions, where the instruction counts are not.

\paragraph{MLLL replacing dual-sum-dual at the response-phase
intersection.}
The response phase computes the intersection
$I_{\mathrm{sk}} \cap \bar{I}_{\mathrm{com}}$ via the dual-sum-dual
identity, which required a working width near $500$~limbs to absorb
HNF coefficient blow-up.  We replaced the HNF reduction with the
modified-LLL (MLLL) of Kim, Lee, and Yoo~\cite{KLY26}, dropping the
working width to $128$~limbs at the main intersection site and
$64$~limbs at the smaller auxiliary one.  Cost scales $O(W^2)$, so
the narrowing is large.  Deterministic measurement: $-11.8\%$ on
signing, output byte-identical.  A follow-up narrowed the widths
further to the $\leq 110$-limb bound proven by Kim et al.\ (ePrint
2025/1649), giving $110$~limbs at the main site and $48$ at the
auxiliary site.

\paragraph{Constant-time modular exponentiation in primality testing.}
\texttt{MontReducer::pow} (Miller--Rabin during the norm-equation
prime search of \texttt{represent\_integer}, where the exponent
$d = (n-1)/2^s$ is secret-derived) was made constant-time: the window
table is read with a scatter-gather \texttt{ct\_select} so the access
pattern does not leak the exponent nibbles, and the final Montgomery
subtracts in \texttt{mul}, \texttt{reduce\_wide}, and
\texttt{compute\_r\_squared} are now branchless.  Output is
identical.  Deterministic measurement: $-1.01\%$ on key
generation, $-0.10\%$ on signing.  Verification untouched.

\paragraph{Montgomery-form Miller--Rabin square-chain unlocks width
narrowing.}
After the witness exponentiation $x = a^d \bmod n$, the strong
probable-prime test squares $x$ repeatedly until it reaches $n-1$ or
exhausts its $s$ steps.  This square-chain was running in canonical
form (a fixed-width $W$-limb multiply followed by a modular
reduction), which truncates the $2\,\mathrm{bits}(n)$-wide product
$x^2$ to $W$ limbs and so demands a working width satisfying
$64W \geq 2\,\mathrm{bits}(n)$: a $273$-bit norm-equation prime was
tested at $W = 10$.  Moving the chain into Montgomery form, where
each step squares via REDC (the full $2W$-limb product folds back
with no truncation, and no per-step division), makes the test correct
whenever the candidate merely fits, $64W \geq \mathrm{bits}(n)$.  The
working-width dispatch then narrows on $\lceil \mathrm{bits}(n)/64
\rceil$ rather than $\lceil 2\,\mathrm{bits}(n)/64 \rceil$, halving
the width: the same $273$-bit candidate now runs at $W = 6$, and
because the per-square cost is $O(W^2)$ the gain compounds with the
removed division.  The decision is unchanged, so all KATs stay
byte-identical.  Instruction-count A/B (Apple M4): $-13.6\%$ on key
generation, $-15.0\%$ on signing.

\paragraph{The same narrowing in Cornacchia's modular square root.}
Cornacchia's algorithm (used to solve the norm equation
$x^2 + q y^2 = m$ once a prime $m$ is found) carries the same
over-provisioned width for the same reason, one layer down.  Its
exponentiations are already in Montgomery form, but the modular
multiplies \emph{between} them in the Tonelli--Shanks square root
(forming products up to $(m-1)^2$ or $(m-1)^3$ before reducing) ran in
canonical form and truncated, again demanding $64W \geq 2\,\mathrm{bits}
(m)$ and so $W = 17$.  Routing those products through Montgomery
multiplication removes the truncation, leaving the only requirement
that $W$ hold $m$, and a width dispatch on $\lceil \mathrm{bits}(m)/64
\rceil$ then runs the same $273$-bit norm-equation prime at $W = 6$.
The narrowing is confined to the prime-search call site, which is
already variable-time; the Montgomery rewrite of the square root itself
is byte-identical and data-independent, so the wider left-ideal square
roots inherit only the correctness cleanup.  All KATs stay
byte-identical.  Instruction-count A/B (Apple M4), on top of the
preceding change: $-3.6\%$ on key generation, $-3.5\%$ on signing.

\paragraph{Fixed-width square root in commitment-ideal sampling.}
The same Montgomery square root has a second beneficiary, on a surface
where the width is fixed rather than narrowed per candidate.  Sampling
a random left ideal of norm $N = D_{\mathrm{mix}}$ (a $513$-bit
\emph{public} parameter) draws a trace-zero quaternion and recovers its
missing coordinate by a Legendre test and a square root modulo $N$,
inside a rejection loop.  Those two operations were running at the
$30$-limb storage width the surrounding lattice columns require, though
$N$ and the reduced operand need only nine limbs.  Since $N$ is a fixed
public bound, not a secret-dependent magnitude, narrowing this modular
arithmetic to nine limbs is data-independent (the same width on every
call), and the Montgomery square root makes it correct.  Output
byte-identical.  Instruction-count A/B (Apple M4): $-4.2\%$ on key
generation, $-0.5\%$ on signing; key generation gains the most because
it builds the secret ideal here, whereas signing samples only the
commitment.

\paragraph{Halving the Montgomery setup ladder.}
Building a \texttt{MontReducer} for a fresh modulus computes $R^2 \bmod n$
(with $R = 2^{64N}$), the constant that converts values into Montgomery
form.  This is done once per modulus, and the prime search builds one
per candidate, so it is a recurring cost.  The naive computation doubles
$1$ up to $2^{128N} \bmod n$ in $128N$ steps; instead we obtain $R \bmod
n = ((2^{64N} - 1) \bmod n) + 1$ with a single division (cheap, since the
all-ones dividend and the modulus are both $N$ limbs, so the quotient is
one or two digits) and double only $64N$ further steps to reach $R^2$,
halving the ladder.  Output byte-identical.  Instruction-count A/B
(Apple M4): $-0.7\%$ on key generation, $-0.6\%$ on signing.

\paragraph{Multiply-accumulate form for the truncated big-integer
multiply.}
The schoolbook \texttt{mag\_mul} (the truncated $N$-limb product
underlying all quaternion-side arithmetic) accumulated each column with
a separate-halves \texttt{widening\_mul} and two carrying additions,
which the compiler lowers to a carry-materialization (\texttt{cset})
per limb.  Rewriting the inner step as a single $128$-bit
multiply-accumulate, $\texttt{result} + a_i b_j + \texttt{carry}$
(whose sum cannot exceed $2^{128}-1$, so the high half is the next
carry), lets the compiler emit a straight \texttt{mul}/\texttt{umulh}
plus an add-with-carry chain.  Portable across targets, output
byte-identical.  Instruction-count A/B (Apple M4): $-7.0\%$ on key
generation, $-2.7\%$ on signing.

\paragraph{Column-scanning multiply on Apple Silicon.}
On Apple Silicon the wide lattice multiplies ($N = 30$, $N = 60$) are
bound by memory traffic, not issue width: the row-scanning multiply
above loads and stores each result limb once per partial product.  An
\texttt{aarch64} assembly kernel reorganizes the schoolbook into
column (Comba) order, holding a $192$-bit column accumulator in
registers and storing one output limb per column, which removes those
per-product round trips.  It is gated to \texttt{aarch64}, so the
instruction-count grade on \texttt{x86\_64} (which keeps the portable
multiply-accumulate above) is unchanged; the kernel trades a few more
register additions for far fewer loads and stores, so it is measured in
cycles rather than instructions.  Output byte-identical (verified
against an independent multi-width reference in addition to the KATs).
Cycle A/B (Apple M4): $-9\%$ on key generation, $-24.6\%$ on signing.

\paragraph{Small-prime trial-division before Miller--Rabin.}
The norm-equation prime search tests a stream of random candidates, the
large majority of which are composite.  Each test was building a
\texttt{MontReducer} (the $R^2$ setup above) and running a modular
exponentiation, even for a candidate divisible by $3$.  The reference's
mini-gmp \texttt{mpz\_probab\_prime\_p} guards its Miller--Rabin chain
with a trial-division pre-screen: it rejects any candidate sharing a
factor with the product $3 \cdot 5 \cdot 7 \cdot 11 \cdot 13 \cdot 17
\cdot 19 \cdot 23 \cdot 29$ before any exponentiation, recovering each
residue $n \bmod p$ from a single reduction of $n$ modulo that product
(mini-gmp caps the product at primes $\le 29$ so it fits a $32$-bit
word; full GMP screens a much larger table).  A candidate caught by the
pre-screen is composite and the witness exponentiation would reject it
too, so the accept/reject decision, and every downstream signature, is
unchanged for any prime set.  We screen two $64$-bit words, primes $3$
through $29$ then $31$ through $73$, which catch roughly $68\%$ and then
$75\%$ of odd composites; the second word's reduction runs only on
candidates the first did not reject.  Output byte-identical (all KATs
green).  Cumulative instruction-count A/B (Apple M4): $-7.0\%$ on key
generation, $-5.2\%$ on signing.  Key generation gains the most because
its prime search issues far more candidate tests per operation than
signing does.

\paragraph{Base-2 Miller--Rabin exponentiation by doubling.}
The strong-probable-prime test runs base 2 first, and that witness is
by far the most executed: it rejects most composite candidates the
norm-equation prime search produces.  The modular exponentiation
$2^d \bmod n$ was using the
general 4-bit fixed-window path, which builds a 16-entry table of
$2^i \bmod n$ (fifteen Montgomery multiplications) and then does one
table multiply per exponent window.  For the fixed base 2 this is
wasteful: a binary square-and-multiply needs no table, and each
``multiply by 2'' is a Montgomery-domain doubling (an $O(N)$ modular
add) rather than an $O(N^2)$ Montgomery multiply.  Specializing the
base-2 case replaces the table build plus the per-window multiplies
with cheap doublings; the squarings, which dominate either way, are
unchanged.  It preserves the constant-time property of the windowed
path: each step squares and computes the doubling unconditionally, then
selects between them with a branchless \texttt{ct\_select} on the
exponent bit, so the secret exponent's bits are not leaked.  The result
is the same $2^d \bmod n$, so the primality decision and every KAT stay
byte-identical.  Instruction-count A/B (Apple M4): $-0.58\%$ on key
generation, $-0.60\%$ on signing.
\paragraph{Hardware AES on aarch64.}
The AES-CTR-DRBG that drives every random draw in key generation and
signing (roughly $3000$ block encryptions per signature) was running
the \texttt{aes} crate's software fixslice backend on aarch64.  The
crate gates its ARMv8 Cryptography Extensions backend behind a
\texttt{cfg(aes\_armv8)} that the build was not setting, whereas the
x86\_64 AES-NI backend is compiled unconditionally and selected at
runtime.  Setting the cfg on the aarch64 target tables lets
\texttt{cpufeatures} runtime-select the hardware backend, with the
software path preserved as a fallback on CPUs lacking
\texttt{FEAT\_AES}.  Hardware AES is constant-time and bit-identical to
the fixslice output, so all KATs stay byte-identical.  Wall-clock A/B
(Apple M4): $-12.0\%$ on key generation, $-3.7\%$ on signing.  Key
generation gains more because the norm-equation prime search issues far
more DRBG draws per operation than signing does.  A time-profile of the
hardware-AES build shows the residual AES cost (about $1.25\%$ of key
generation, less of signing) is dominated by the AES key schedule, not
block encryption.  The DRBG was also switched from the full
\texttt{aes::Aes256} cipher to the encryption-only \texttt{Aes256Enc},
since CTR mode never decrypts; this drops the wasted decryption key
schedule and is the correct cipher type for the construction.

\paragraph{One key schedule per DRBG generate cycle.}
The key-schedule cost above is one AES-256 expansion per
\texttt{CTR\_DRBG\_Generate}: the \texttt{Key} changes on every
\texttt{Update}, so one expansion per cycle is mandated by SP 800-90A
and is not byte-identically removable.  The implementation was doing
\emph{two}, though: \texttt{randombytes} expanded the key for its
generate loop, then the trailing \texttt{Update} (which encrypts under
the same, not-yet-changed \texttt{Key}) expanded it again.  Sharing the
one schedule across both loops halves the per-cycle expansion; the
generate loop was also switched from one-block-at-a-time
\texttt{encrypt\_block} to batched \texttt{encrypt\_blocks} so the
backend's parallel pipeline is fed.  Output is byte-identical (all KATs
green).  Profiled on an Apple M4, the key-schedule self-time in key
generation fell from about $1.05\%$ to $0.50\%$ of the total, with the
generate-loop encryption falling below the sampling threshold.

\paragraph{Branch-free reductions on the secret-quaternion-action path.}
Two adjacent one-bit leaks fired on derived bits of the secret
response quaternion $\alpha$:
(a) \texttt{EvenResponseKernel::from\_quaternion} (\S\,Alg. 4.6)
picked one of two columns of $M_\alpha$ for the kernel scalars
$(s, t)$ on the parity of $\gcd(s_0, t_0)$;
(b) \texttt{EndomorphismAction::apply} canonicalized each
truncated-mod remainder via \texttt{if r.is\_negative()}.
Both rewritten as branch-free \texttt{conditional\_select}s.
Byte-identical across $100/100$ sign KATs.  The residual variable-time
\texttt{BigInt::gcd} on $(s_0, t_0)$ in (a) is a separate
\texttt{TODO(ct)}, deferred to the divstep wiring pass.

\paragraph{Proven-width size-reduction multiplies in MLLL.}
Each MLLL size-reduction step (the lazy size-reduction, Alg.~8
of~\cite{KLY26}) subtracts $\lfloor\mu_{\kappa,i}\rceil\,b_i$ from the
working vector and applies the matching symmetric rank-one update to its
Gram row, running a handful of products of the integer coefficient
$\lfloor\mu_{\kappa,i}\rceil$ against a basis coordinate or a Gram entry.
At fixed-width \texttt{BigInt} these are full $N\times N$ schoolbook
products at the working width $W=N$ ($110$ limbs at the main
intersection, $48$ at the auxiliary one), although the operands are far
narrower.  The C reference avoids the waste implicitly (its
\texttt{mpz} arithmetic multiplies only the significant limbs of each
operand), but that is variable-time in the operand magnitude, a timing
leak on this secret-derived path.  A fixed, \emph{provable} width bound
recovers the saving without the leak.

\begin{lemma}\label{lem:mlll-widths}
In the MLLL reduction over fixed-width $\mathtt{BigInt}\langle N\rangle$
at working width $W=N$, every basis coordinate occupies at most $N/2$
limbs and every size-reduction coefficient $\lfloor\mu_{\kappa,i}\rceil$
at most $N/2+1$ limbs.
\end{lemma}

\begin{proof}
Let $B$ be the largest-input-norm$^2$ bound that sizes the working
width, so every intermediate integer satisfies $|x|<2^{64N}$, hence
$\sqrt{B}<2^{32N}$.  A basis coordinate is bounded by its vector norm,
$|b[r]|\le\lVert b\rVert=\sqrt{\langle b,b\rangle}\le\sqrt{B}<2^{32N}$,
so it occupies at most $N/2$ limbs.  For the coefficient, Cauchy--Schwarz
and the $L^2$ Lov\'asz invariant on the already-reduced prefix give
\[
  |\mu_{\kappa,i}|\le\frac{\lVert b_\kappa\rVert}{\lVert b_i^\ast\rVert}
  \le\frac{\sqrt{B}}{(\bar\delta-\tfrac14)^{(G-1)/2}},
\]
using $\lVert b_\kappa\rVert\le\sqrt{B}$, the Lov\'asz bound
$\lVert b_i^\ast\rVert^2\ge(\bar\delta-\tfrac14)^{\,i-\zeta}
\lVert b_\zeta^\ast\rVert^2$, and $\lVert b_\zeta\rVert\ge1$ for the
nonzero integer vector $b_\zeta$.  With $\bar\delta=0.995$ and $G\le16$
the denominator exceeds $2^{-4}$, so $\lfloor\mu_{\kappa,i}\rceil<
2^{32N+4}$, which fits in $N/2+1$ limbs.  Both bounds depend only on $N$
and the $L^2$ constants, not on the operand values.
\end{proof}

The bounded multiply exploits Lemma~\ref{lem:mlll-widths}: the column
update multiplies two $\le N/2$-limb operands ($(N/2)^2$ partial
products instead of $N^2$), and the Gram update an $N/2$-limb coefficient
against a full-width entry ($(N/2)\,N$).  The trip counts are fixed by
those widths, with no branch on a secret coefficient's magnitude, so the
narrowing the reference performs variably becomes constant-time and leaks
nothing through timing.  Output is byte-identical across all $100$
signing KATs.  Hardware instruction count (\texttt{/usr/bin/time -l}):
$-12.9\%$ on signing.

\subsection{Rejected alternatives}
\label{sec:tried-rejected}

Each alternative below was evaluated and not adopted.  We record the
reason in each case, since a documented dead end is itself a design
decision and spares a reader the same one.

\paragraph{Cost-optimal isogeny strategy for the verify-side 4-isogeny
chain.}
The verify-side $2^e$-isogeny chain in
\texttt{src/curves/isogeny/mod.rs} (decomposed into
$\lfloor e/2 \rfloor$ 4-isogenies) was changed from runtime
balanced halving to a compile-time-precomputed cost-optimal De
Feo--Jao--Plut strategy.  Output is byte-identical.
Deterministic measurement:
$-0.04\%$ on verification, $0$ on key generation and
signing: no measurable gain, because verification's hot path
is $\mathbb{F}_{p^2}$ and elliptic-curve arithmetic, not the strategy
walker, at our chain length ($e \leq 126$).

\paragraph{Cost-optimal strategy on the $(2,2)$-theta chain (surfaces).}
The same DP strategy was applied to Phase~1 of the $(2,2)$-theta chain
in \texttt{src/surfaces/mod.rs}.  A large fraction of the lib tests
failed, including the majority of signing KATs.  Root cause: Phase~1 uses the
non-standard Jacobian doubling \texttt{double\_for\_theta} (with
$Z' = 2yz$) deliberately, so the gluing step receives the specific
projective representative the C reference produces.  Reordering the
doublings within the strategy walker changes the cumulative $Z$
scaling, which the gluing matrix multiplies by, which then changes the
produced signature bytes, even though the composed isogeny is
mathematically unchanged.  The reordering is therefore confined to a
future non-interoperable release.

\paragraph{Batch inversion in \texttt{cross\_pairings} final
exponentiation.}
The five independent $\mathrm{den}^{-1}$ inversions in the
\texttt{cross\_pairings} final-exponentiation loop were folded into a
single inversion via Montgomery's trick.  Output is identical and
every KAT byte-identical.  However deterministic measurement showed
a $+0.05\%$ regression overall and $+0.62\%$ on verification: the
two-pass refactor's overhead
(extra $\mathbb{F}_{p^2}$ array storage, a likely inlining-decision
change in a now-larger function) exceeded the savings from fewer
inversions, given how rarely \texttt{cross\_pairings} is invoked per
signing operation.

\paragraph{Substituting MLLL into ideal multiplication.}
Replacing the HNF step in \texttt{Lattice::product} with MLLL on the
same theory as the intersection win.  In practice the multiplication
runs at small widths where MLLL's fixed overhead (a $16 \times 16$
Gram matrix and the iterative reduction) exceeds the modest HNF
blow-up it removes.  Result: roughly $1.9\times$ regression on
key generation in a controlled A/B.

\paragraph{Input-LLL preprocessing of the intersection.}
The input-LLL preprocessing of~\cite{KLY26} reduces each input basis
before dualization, intending to bound the duals' cubic coefficient
growth.  Our existing \texttt{l2\_reduce} routine minimizes the
reduced-norm form $a^2 + b^2 + p\,(c^2 + d^2)$, which is the natural
norm in $B_{p,\infty}$ but is dominated by the $p\,(c^2 + d^2)$ term;
the coordinate magnitudes that drive the Euclidean blow-up therefore
remain unbounded under our reduction.  The intersection width did not
fall below $128$~limbs and the experiment was shelved pending a
Euclidean reduction step (the constant-time dim-4 LLL of Hanyecz et
al., ePrint 2025/027, is the intended substitute).

\paragraph{Hanyecz constant-time dim-4 BKZ-2 as preprocessing in front
of the MLLL intersection.}
Hanyecz et al.\ (ePrint 2025/027) give a constant-time dim-4 BKZ
with block size $2$ as the Euclidean-norm replacement for
\texttt{l2\_reduce} on secret-derived inputs.  We ported their five
algorithms (\texttt{src/quaternions/lattice/bkz2.rs}) and invoked them
in front of \texttt{compact\_intersection} at the two response-phase
call sites of \S\ref{sec:perf-ct}; output stays byte-identical with the
C reference, since the canonical HNF depends only on the inputs'
$\mathbb{Z}$-modules, not their basis representatives.

The preprocessing does not help here.  MLLL already runs at the proven
width bound of~\cite{KLY26}, a property of the lattice rather than of
any basis representation, so BKZ-2 cannot narrow it further; across
every parameter setting it added cost and regressed signing wall-clock
by roughly an order of magnitude.  Separately, the paper's own proposed
use (substituting for \texttt{l2\_reduce} on secret-derived inputs)
is KAT-breaking, since the surviving \texttt{l2\_reduce} call sites
feed basis-dependent downstream logic.  Capturing that constant-time
win therefore requires a KAT re-baseline, bundled with the Cornacchia
fix (ePrint 2025/2192) and the fast-primality items (\S\ref{sec:next})
into a single non-interoperable release.  The BKZ-2 algorithms are
retained as a self-contained library; only the integration is deferred.

\paragraph{Whole-program LTO with a single codegen unit.}
A \texttt{[profile.release]} with \texttt{lto = "fat"} and
\texttt{codegen-units = 1} was tried on the theory that cross-crate
inlining of the \texttt{aes}, \texttt{subtle}, and field kernels would
help.  It regressed both hot operations relative to the default
sixteen-codegen-unit build: wall-clock A/B (Apple M4) of $+6\%$ on
signing and $+5\%$ on key generation.  The single codegen unit appears
to make worse register-allocation and inlining choices in the MLLL and
lattice-product inner loops than the per-unit default.  Output is
byte-identical; the regression is pure codegen, so the default
multi-unit build is retained.

\paragraph{Byte-identical micro-optimizations with no wall-clock
effect.}
Three byte-identical changes measured neutral (within run-to-run noise)
on an Apple M4 and were not adopted as performance work: (a) a
stack-allocated $16$-element array in place of the \texttt{Vec}
accumulator in \texttt{Lattice::product} and its modulus variant,
removing the heap reallocations of the $16$-column product but not
moving wall-clock; (b) fusing the doubling and conditional-subtract
limb passes in the $R^2$ Montgomery-setup loop; and
(c) strength-reducing the multiply-by-$p$ in the MLLL Gram computation
to $(x \ll 250) + (x \ll 248) - x$ (using $p = 5\cdot 2^{248} - 1$),
which at the $110$-limb response-phase width is no faster than the
length-aware schoolbook multiply by the four-limb constant it
replaced.

\subsection{Next steps}
\label{sec:next}

\begin{enumerate}
  \item Costello--Hisil 4-isogeny formula and Renes square-root-free
    2-isogeny formula in the elliptic factors (verify-side chain),
    composed underneath the cost-optimal strategy already in place.
  \item Leroux CRT intersection~\cite{basso2025}, replacing the
    dual-sum-dual identity entirely; the roadmap claims
    signatures-identical, but the surfaces $(2,2)$-theta result above
    means this should be verified with a small prototype before the
    full substitution.
  \item Continue the constant-time hardening sequence
    (\S\ref{sec:ct}).  The remaining variable-time surfaces are
    \texttt{MontReducer::pow}'s base reduction
    (\texttt{mag\_div\_rem}), Cornacchia in the norm-equation search
    (ePrint 2025/2192, the highest-severity item, poly-time key
    recovery from the input leak), and \texttt{l2\_reduce} on
    secret-derived input (where the Hanyecz BKZ-2 substitution above
    is the intended fix, bundled with the other KAT-breaking CT items
    into a single non-interop release).
  \item In-place / out-parameter refactor of the hot wide-\texttt{BigInt}
    lattice operations to remove struct-copy overhead
    (\texttt{memcpy} is $\sim\!13.5\%$ of signing).  The arithmetic
    returns values by move: \texttt{Lattice::product},
    \texttt{Vector}/\texttt{Matrix} operations, and the \texttt{BigInt}
    operators all return new wide structs (a $4\times 4$
    \texttt{Matrix} of $30$-limb integers is $\sim\!3.8$~KB), copied on
    every compose in the HNF / intersection loops.  The C reference
    avoids this with an out-parameter, const-reference convention
    (\texttt{op(out, a, b)}, e.g.\ \texttt{ibz\_vec\_4\_add}); adopting
    in-place variants for the hot wide operations is the corresponding
    structural lever, and is interop- and constant-time-safe.  Unlike
    the assembly attempts (\S\ref{sec:backends}), it is a portable,
    all-architecture change.
\end{enumerate}
